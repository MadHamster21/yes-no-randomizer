YES/NO RANDOMIZER — DATA SAFETY REVIEW
23 November 2026

Status

Release 3.6 (27) was rejected. The owner reports that Data safety currently
answers No to collecting/sharing required user data types. Both the Console
evidence and rejection email identify Email Address for version 27 but provide
no SDK, destination, field name or reproduction trigger.

The No answer does not cover Google's documented ML Kit telemetry. That known
disclosure gap does not establish the cause of the specific email finding.

Reviewed evidence

- Source changes since the 3.5 preparation commit 9162c8a: local language
  preference resolution, UI/lifecycle/build dependency updates, and versioning.
- The saved signed app/release/app-release.aab declares version 3.6, code 27.
  Its dependency metadata confirms Translate 17.0.3, Language ID 17.0.6,
  ML Kit Common 18.11.0, Compose UI/Runtime 1.13.0, Material3 1.5.0,
  and Lifecycle 2.11.1.
- Translate and Language ID's declared versions were unchanged from 3.5.
- No Firebase Auth, Google Sign-In, Firebase Analytics, Crashlytics or
  Google Mobile Ads artifact was found in the reviewed bundle metadata and
  resolved runtime graph. This does not by itself prove that no SDK can ever
  transmit an email address.
- The app has no account/email input feature or developer-operated API endpoint.
  The translation wrapper calls the on-device ML Kit APIs. Its Google Translate
  attribution link opens the external browser with a static URL and no question.
- The merged release requests INTERNET, ACCESS_NETWORK_STATE, and the app's
  internal DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION. Service/receiver protection
  attributes such as BIND_JOB_SERVICE or DUMP are not requested user permissions.
- No decrypted network-payload audit has yet been completed for this rejection.
  Do not describe the email allegation as a proven false positive.

What changed in the dependency updates

Compose BOM: 2026.09.00 -> 2026.11.01, selecting Compose UI/Runtime 1.13.0
and Material3 1.5.0 in the current bundle.
Lifecycle: 2.11.0 -> 2.11.1. Google's documented patch fixes currentStateFlow
instance reuse. No email-collection requirement is documented in that patch.
AGP: 9.4.1 -> 9.5.0 -> 9.5.2. Gradle: 9.6.1 -> 9.9.1.
AGP and Gradle run on the build workstation, not as app SDKs on users' phones.
compileSdk moved from 37.0 to 37.1 for Compose's compilation requirement;
targetSdk remained 37 and minSdk remained 24.

Official release notes reviewed do not identify a new email-collection
requirement in these upgrades. This finding is based on source/dependency
inspection and documentation, not a guarantee about all runtime behaviour.

Form references — not a completed questionnaire

Collect/share required user data types: Yes is needed for the documented SDK
telemetry. Collection includes SDK transmissions even when the developer does
not receive a copy. On-device-only question processing is distinct from that
telemetry.

Review Device or other IDs (installation identifiers), App info and performance
(diagnostics/performance), and the appropriate App activity category for SDK
usage events against the provider's descriptions. Do not automatically select
every nearby data category, or call the data anonymous because IDs are random.

For each selected category, verify collection, sharing, purpose, optional versus
required, ephemeral processing, encryption and deletion separately. Provider
statements about onward sharing do not replace applying Play's definitions to
the app's actual processing. A language-download choice is not a telemetry
opt-out. No blanket server-side deletion or 90-day retention promise was verified.

Email Address: unresolved. Obtain the reviewer's collection source/endpoint or
complete a release-behaviour/network audit using synthetic test data. If email
collection is verified, disclose and describe it accurately or remove its source.
If it cannot be substantiated, request clarification/review using the technical
findings. Do not select Email Address merely to make the rejection disappear.

The Families commitment question controls a voluntary listing badge, not whether
Families obligations apply. The owner confirmed ages 6-8, 9-12, 13-15 and 16-17,
and no Teacher Approved participation. SDK suitability and any applicable consent
requirements still need review; the policy draft does not certify compliance.
The old policy's under-13 exclusion conflicts with the confirmed child audience.

The owner also confirmed handling and then deleting support emails, rather than
maintaining an app customer-email database. The revised draft reflects that
practice and distinguishes it from Google's SDK-metrics retention.
